# Builder notes

## v4 (2026-10-03) — daily game, English only, MAU plumbing

### Deviations from BRIEF_web_v4.md and docs/api-daily.md
1. **Schema beyond the brief's column lists** (`migrations/0003_daily.sql`): `plays.streak` (streak = the previous day's streak + 1, one primary-key read, so completing never reads a player's history); `daily_agg.patterns` (32 counts by hit bitmask over the day's five items: retiring an item recomputes `hits_hist` from this row alone, so the flag path never scans plays or answers); `items_runtime.n_log_err` (count behind the running mean, because the log error is undefined for some answers); `sessions.anon_id` (next item). `players.community` as the brief asks.
2. **MAU counts full assessments (PREREG wins over "from plays").** PREREG: "completed play (full assessment or daily game)". The browser sends its daily-game id (`hs_anon`) with `/api/submit`; the KPI job counts distinct ids over daily plays (on their game day) plus sessions that carry an `anon_id` (on the day they finished; surface `classroom` when they had a class code, else `web`). Sessions without an `anon_id` (older clients, API calls such as the smoke test's) have no anonymous id and are not counted; the current web client always sends one. DAU likewise for one day. Workspaces = distinct Slack `community` values among plays in the window; classrooms = class codes with ≥ 5 completed sessions (all-time, as PREREG; attention failures included, like the class dashboard). `/api/kpi/run` takes an optional `?as_of=` (default today); the cron Worker sends yesterday at 00:10 UTC.
3. **Contract details the docs leave open:** `anon_id` is opaque, 1-64 characters of `[A-Za-z0-9_-]` (web: 22 random; Slack: 64-char sha256 hex). `community` is accepted on answer and complete and stored on `players` (an answer that carries one creates the player row with `plays = 0` until a play completes; web ignores it). Answer and complete accept today or yesterday (UTC) only, else 400; a valid date with no game is 404. `GET /api/daily` and `/api/daily/stats` accept any scheduled date up to today; future dates are 404, so items never leak early. `hit` is a boolean. `log_ratio_error = log10(((low + high) / 2) / truth)`, rounded to 6 decimals, signed (positive = range centred above the truth), `null` when the midpoint or the truth is not positive (e.g. melting points below 0 °C); `items_runtime.mean_log_err` averages its absolute value. "Passed plays only" for `/api/daily/stats` is read as completed plays (the daily game has no attention checks). Complete needs every non-retired item answered (400 otherwise); a repeat complete returns the stored streak, hits/n rescored from the stored answers without retired items, and fresh day stats. One play per id and day whatever the surface. The share URL is the request origin.
4. **Flags need an answer.** `POST /api/flag` is accepted only from an id that answered that item on a scheduled day up to today (403 otherwise): every pool id is public in `pool.json`, so without this three made-up ids could retire tomorrow's items. A retired item is left out of `GET /api/daily`, of scoring and of the day's histogram; answers to it are kept.
5. **Pool item shape adds `category`** (the rotation group for "max 1 per category per day"; the brief's item template has no field for it). Related queries share a group: lake area + lake depth = `lake`; planets' and moons' distances = `solar_system_distance`. `accept` is a fixed sanity range per query (e.g. mountains 0-9,000 m), never derived from the answer, because a range centred on the answer would give it away; entities outside it are dropped.
6. **Pool contents** (live run 2026-10-03, 15 queries, 2,074 items): independence years were not generated, because Wikidata has no consistent property for them ("inception" records other events: Mexico 1810, Nigeria 1963). Moons are a named list of 26 well-known moons (Wikipedia sitelinks cannot tell them from tiny moons; bots inflate those). Popularity cut-offs (sitelinks) and caps per query are in `wikidata_pool.py`. Preferred statements win; among the best-ranked values, more than 2% disagreement = conflict = skipped. Some kept items are obscure or odd (e.g. "Tanners' Bridge", 8 m); that is what the nightly review is for.
7. **`public/pool.json` holds id, category, prompt and unit only**: no answer, no `accept`, and no source, because the Wikidata link shows the answer.
8. **`functions/_schedule.json`** (a synced copy of `daily/schedule.json`) is how the API knows each day's items; schedule edits need a sync and a deploy.
9. **Day #1 is 2026-10-17 (soft launch; the coordinator's change after the v4 build, replacing the brief's 2026-10-20), and earlier days show #0** (`dayNumber` clamps at 0). The schedule starts 2026-10-03, so preview days share as `HowSure #0`. Oct 17–31 were hand-curated by the coordinator. Tests derive their fixture dates from `EPOCH`; only the day-number test pins 2026-10-17. The live schedule is checked only as sync-items checks it (dates, 5 distinct pool ids), not against the generator's category/reuse rules, so hand curation cannot break `npm test`. Generation is append-only (existing days, past or future, are never changed), seeded by date, least-recently-used category first with ties broken by use count; the difficulty mix reads an optional `daily/runtime.json` exported from D1 (format in README).
10. **`robots.txt` has only a `Sitemap:` line.** The acceptance grep forbids the string "user-agent" in `public/`, and a file with no groups allows every crawler (RFC 9309). The sitemap lists extensionless URLs (Pages serves `tests/x.html` at `/tests/x`) on `https://howsure.me` — change it if the site lives elsewhere.
11. **`web/.gitignore`** lists the generated pool and schedule copies (the root `.gitignore` is outside this builder's folders).
12. **Range warnings no longer name the button** ("press the button again"), since the daily game's button says "Lock in".
13. **Join links point to `/test?c=CODE`**; `/` is the daily game.

### Known limits (v4)
- A complete that commits while an item is being retired keeps its pre-retirement histogram bucket until that day's next recompute (`patterns` stay exact).
- `plays.hits` and `plays.n` are frozen when the play completes; after a retirement they are stale (the API rescores from `daily_answers`, and so should the research analysis, which excludes retired items anyway).
- The KPI row for a day is computed at 00:10 UTC the next morning; a yesterday's-game completion sent after that counts in the next run's window but not in that day's stored DAU.
- `GET /api/kpi` is browser-cached for 5 minutes; `/api/daily/stats` is cached 60 s per data centre (the flag path does not purge it).
- Not updated (outside this builder's folders): `PRIVACY.md` (needs a daily-game paragraph; its "bilingual" sentence is out of date), `docs/api-daily.md` (it now lists `community` and the date rule, as implemented), root `README.md` (still says English and Chinese).
- Verified only on local workerd (`wrangler pages dev`), not on Cloudflare. `npx wrangler pages functions build` compiles the Functions bundle to 720 KB (70 KB gzipped, including the 652 KB pool); nothing was deployed, so the deployed bundle, Cache API on `*.pages.dev` and the cron Worker against a live site are unverified.
- Browser checks: Chromium at 375 px (daily game end to end, resume after reload, flag, share card, stats with and without KPI data, `/test`, an explainer page). Not checked on iOS Safari or in-app browsers; clipboard copy not exercised in the preview.

## v0.1 — deviations from the brief (smallest sensible change each)

1. **No `functions/api/class/d/[secret].csv.js`.** Wrangler orders `/api/class/d/:secret` before `/api/class/d/:secret.csv` and runs only the first match, so the CSV route was unreachable (`next()` falls through to static assets; verified with wrangler 4.147.0). `[secret].js` serves the CSV when the path ends in `.csv`. The URL is unchanged.
2. **Metrics live in `public/metrics.js`;** `functions/_metrics.js` re-exports it, so the API, the browser and the tests use one file (the browser cannot load files under `functions/`). The browser imports the confidence levels from it; every score is computed server-side.
3. **Extra files:** `public/ui.js` (auto-escaping HTML template, fetch wrapper, localStorage wrapper, SVG charts) and `public/_headers` (CSP `default-src 'self'`, nosniff, no-referrer). `test/unit.test.js` holds the non-metric unit tests; `npm test` runs both test files.
4. **`first_session_id` is sent on every later session from the same browser.** The browser keeps its first session id in localStorage (`hs_first`). This is what lets PREREG's exclusion "repeat sessions from the same browser identifier (keep the first)" be applied. (v4: the bilingual re-take that also used it is gone.)
5. **Seen items** are kept in localStorage (`hs_seen`); later sessions avoid seen two-choice and range items while enough remain. Attention items are never excluded (every session needs both).
6. **Class dashboard counts every completed session with the code,** including attention failures; `n` and all aggregates use that same set. `/api/stats`, `global` and percentiles use passed sessions only.
7. **Attention items look exactly like two-choice items** (answer + confidence) so they blend in; their confidence never enters a metric.
8. **Range input:** low > high is warned once, then swapped; values outside the item's `accept` bounds are warned once, then kept (PREREG excludes them at analysis time). Empty or non-numeric input always blocks. The server rejects only non-finite numbers and low > high; it does not reject fast answers or out-of-bounds ranges.
9. **Honeypot:** the hidden form field is named `hs_extra` (so browser autofill leaves it alone) and is sent to the API as `website`.
10. **Running aggregates (follow-up request, 2026-10-03).** `migrations/0002_aggregates.sql` adds `agg_totals`, `agg_hist`, `agg_bins`, `agg_country`; `functions/_aggregates.js` holds the bins, the histogram percentile and the upserts. A submit is one `env.DB.batch()` (one transaction): read the language's histogram (≤ 28 rows), insert the session, then 4 upserts. Only sessions that passed both attention checks are aggregated. `/api/stats` reads only the aggregate tables (still cached 60 s); `n_countries` = `agg_country` rows except `ZZ`/`XX`/`T1`. No backfill: aggregates start empty, so 0002 must be applied before real traffic (true today; a local dev DB with older sessions should be recreated). Class dashboards still read their own class's sessions; `EXPLAIN QUERY PLAN` (checked in smoke.sh) shows `SEARCH sessions USING INDEX idx_sessions_class`. The `sessions(lang, passed_attention)` index is no longer used by the API but is kept as the brief asks (one extra index row per insert; useful for analysis queries).

## Definitions the brief left open

- Stored `answers` JSON: `{id, type, choice, conf (50–100), rt_ms, correct}` or `{id, type, low, high, rt_ms, hit}`; `correct`/`hit` are server-computed. `/api/stats` aggregates bins from it with `json_each`.
- Score columns are rounded to 6 decimals, so equal scores compare equal in the percentile query.
- `n_answers` = scored answers in passed sessions (18 per session; attention items excluded).
- `percentile.overconf` = mid-rank from `agg_hist` among same-language passed sessions, current session excluded: share of sessions in lower bins plus half of your own bin. Overconfidence bins are 0.05 wide (`round(overconf × 20)`, clamped to ±10, i.e. ±0.5), so sessions within the same 0.05 band count as ties; hit-rate bins are exact (`round(int_hit × 6)`). Copy: "more overconfident than p%" / "caught the answer more often than p%". `null` below 30 sessions.
- `n_countries` excludes Cloudflare's non-country codes `ZZ`, `XX`, `T1`.
- `overconf_hist`: 15 buckets of 10 percentage points from −50 to +100 (lower bound inclusive, values outside clamped to the end buckets).
- Results headline: three cases (more / less / equal, after rounding to whole points).

## Known limits (not fixed, by design or out of scope)

- **D1 quotas.** Reads are bounded per request since change 10 (about 40 rows per submit, a few hundred per uncached stats call). Writes are now the binding limit: about 8–13 rows per finished test (session + 2 index entries + up to 10 aggregate rows), so the free tier's 100K rows written per day covers roughly 7,500 finished tests a day; past that D1 refuses writes until midnight UTC. Upgrade to Workers Paid before a launch post that could exceed it.
- smoke.sh reads fresh stats by asking through `localhost` instead of `127.0.0.1`: the Cache API key is the full URL, so another host name skips the 60 s cache.
- **Cache API** is verified locally only. If it turns out to be a no-op on `*.pages.dev`, `/api/stats` is computed on every call (a few hundred rows read each, same results); a custom domain avoids the question.
- **No rate limiting in code** (Pages Functions have none built in). Add a Cloudflare WAF rate-limiting rule for `/api/*` after deploy.
- SPA routing relies on Pages' default (no `404.html` → `index.html` for `/stats`, `/class`, `/class/d/…`); verified in `wrangler pages dev`.
- Browser checks were done in Chromium at 375 px (landing, items, validation, demographics, results, en/zh share cards in both sizes, class pages, dashboard, stats). Not checked on real iOS Safari or the WeChat in-app browser.
- `compatibility_date = 2026-09-01`; wrangler 4.147.0 accepted it without warnings.
